# Valen architecture review — 2026-08-03

## Scope

This review follows the addition of ownership rules, contracts, generics, native tests,
short-circuit expressions, and iterable `for` loops. It evaluates whether the current
compiler should be reorganized before more language features are added.

Current implementation size is approximately 12,700 lines. The largest components are:

| Component | Bootstrap | Self-hosted |
| --- | ---: | ---: |
| x86-64 backend and runtime | 1,950 lines | 2,202 lines |
| Semantic analysis | 1,606 lines | 1,784 lines |
| IR generation | 832 lines | 1,278 lines |
| Parsing | 555 lines | 491 lines |

## Decision

Do not perform a broad rewrite or attempt to share implementation code between the
JavaScript and Valen compilers. Their independence is part of the bootstrap proof.
The frontend remains readable, and its direct control flow is currently an asset.

Refactor the contracts *between* phases instead. The most valuable work is to make IR,
diagnostics, runtime ABI, and cross-generation behavior explicit and mechanically
checkable. This catches drift without hiding the language behind a large abstraction
framework.

## Findings

### 1. IR is the highest-risk boundary

Both generators construct loosely validated instructions by assigning operation-specific
fields after creation. Both backends then interpret those fields through large operation
dispatch functions. A missing result type, target, block label, argument, or ownership
annotation is generally discovered late in assembly generation—or in the executable.

Recent control-flow features also synthesize calls directly. That makes it easy for a new
construct to accidentally bypass normal virtual or contract dispatch rules. The solution
is not a new AST framework; it is one validated IR vocabulary and shared call-construction
helpers inside each compiler implementation.

**Priority: immediate.** Implement issue #47 before optimization passes or another backend.
Validation should cover unique symbols and blocks, valid branch targets, defined values,
required instruction operands, type-consistent results, call arity, and valid entry/type
references. Canonical construction helpers should own direct, virtual, and contract calls.

### 2. Cross-generation parity is tested too coarsely

The JavaScript suite has broad feature coverage, but most assertions inspect bootstrap
semantic objects, IR, or assembly. Only a small native corpus is compiled by generation 1.
This leaves room for the self-hosted AST, semantic model, and IR to drift while the Docker
bootstrap still succeeds.

**Priority: immediate after IR validation.** Issues #48, #50, and #55 should share one
table-driven fixture corpus. Each valid fixture should compile through both generations;
selected fixtures should compare normalized IR and runtime results. Invalid fixtures should
compare stable diagnostic codes and source spans rather than prose alone.

### 3. The self-hosted AST is approaching its flexibility limit

The bootstrap AST uses dedicated node classes. The self-hosted AST uses broad `Statement`,
`Expression`, and `MemberDeclaration` objects with string kinds and many nullable fields.
That was an excellent bootstrap shortcut, but each new construct expands the set of field
combinations that must remain valid by convention.

**Priority: before substantially richer expressions or pattern matching.** Introduce typed
node-kind constants and narrow construction functions first. Split the broad nodes only
when those constructors reveal stable families. Avoid a visitor hierarchy until multiple
passes demonstrably benefit from it.

### 4. Semantic built-ins are distributed across several branches

Arrays, strings, builders, hashing, native functions, and iteration are recognized in
multiple expression-analysis and lowering paths. Adding a built-in operation requires
remembering every stage in both compilers.

**Priority: medium.** Create a small per-implementation built-in registry describing method
name, receiver shape, parameters, result type, ownership behavior, and IR operation. Keep
special control-flow constructs such as short-circuiting and iteration explicit.

### 5. The backend contains several separable responsibilities

Each x86-64 implementation performs frame layout, instruction emission, object metadata,
garbage-collection support, strings, arrays, filesystem/process facilities, and assembly
data generation in one large component. This is the largest maintenance surface and will
make ABI stabilization or another architecture unnecessarily risky.

**Priority: after issue #54 defines the ABI.** Separate an architecture-neutral runtime
contract from x86-64 instruction emission, then split runtime facilities by responsibility.
Do not split merely to reduce file length; split along testable ABI boundaries.

### 6. Optimization refactors need measurements first

Linear symbol storage and immutable assembly strings are visible costs, but there is no
baseline showing which cost dominates compilation. Replacing them now could make the
self-hosted compiler less readable without materially improving bootstrap performance.

**Priority: deferred.** Complete issue #42 before #36, #37, or #38. IR validation may then
support #44 safely; register allocation should remain later.

## Recommended sequence

1. **#47 — IR validation and canonicalization.** Establish the compiler/backend contract.
2. **#48 + #50 + #55 — cross-generation conformance corpus.** Detect semantic drift.
3. **#54 — stabilize the x86-64 Linux ABI and runtime boundary.** Enable backend separation.
4. Add typed self-hosted AST constructors when the next rich expression feature begins.
5. **#42 — measure performance** before restructuring allocation or symbol storage.

## Practices for future evaluation rounds

Run another review after any major type-system change, backend addition, or roughly five
substantial language features. Record component sizes, cross-generation coverage, known
phase-boundary invariants, and whether the previous review's risks actually materialized.
Architecture reviews should produce small follow-up tickets, not an open-ended rewrite.
